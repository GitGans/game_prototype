Остальные layers (`shared, data, battle, ui, objects, scenes, core, progression, inventory, campaign`) сохраняют `policy.kind === 'blocklist'` без изменений в списках `banned`. Добавлено обнаружение непокрытых top-level слоёв: чистая функция `findUncoveredLayers()` (`scripts/layer-coverage.mjs`) сравнивает директории, реально существующие в `src/` (`readdirSync`), со списком `RULES.map(r => r.root)` и с `LAYER_COVERAGE_EXCLUSIONS` (сейчас пуст — все текущие top-level директории покрыты правилами); exclusion без непустого `reason` не подавляет ошибку. Оба модуля покрыты фокусированными тестами: `tests/scripts/boundaryPolicy.test.ts`, `tests/scripts/layerCoverage.test.ts`. **Важное ограничение, которое покрытие НЕ доказывает:** layer coverage гарантирует только *наличие* правила для каждой директории — она не проверяет, что существующие blocklist-правила образуют полную и взаимоисключающую матрицу зависимостей. Если позже появится, например, `save/`, у которого будет свой rule (coverage удовлетворено), ничто не заставит blocklist других существующих layers (`battle`, `campaign` и т.д.) добавить `'save'` в свой `banned` — они могут начать молча импортировать `save/`, и проверка останется зелёной. `world/**` не подвержен этому конкретно благодаря allowlist-модели; остальные layers — да. Это осознанно задокументированное, а не скрытое ограничение. `PURE_CORE_FILES` остаётся отдельным per-file enforcement и не считается directory coverage. |

Единственный application seam — `applyBattleLifecyclePhaseAction({ source, state, action })` в `phaseHandlers/battlePhaseHandler.ts`: он вызывает чистое `applyBattleLifecycleAction`, и только при сигнале `persistPlayerPlacements` (переименован из `persistCampaignPlacements`) резолвит хранилище через `PlayerSessionStore`. `PhaseManager` больше не читает этот сигнал, не содержит цикла по unit/deployment и не обращается к `GameState.getCampaignState()`/`replaceCampaignRoster()` на этом пути — он вызывает одну lifecycle-функцию и ставит runtime. Персистится **pre-action** `runtime.state` (подтверждённая игроком расстановка) до установки боевого runtime, поэтому throw оставляет фазу, runtime и roster нетронутыми. Контракт закреплён тестами: `tests/core/playerUnitPersistence.test.ts` (правило преобразования), `tests/core/battleLifecyclePhaseAction.test.ts` (маршрутизация: debug пишет только в debug, campaign только в campaign, отклонённый begin-combat не пишет никуда), `tests/battle/combatStart.test.ts` (сигнал). **Не достигнуто и не входило в стадию:** exit-персистентность (HP/life-state/level/placement) остаётся route-specific и campaign-only до Stage 8; `applyBattleExitPlayerPersistence` продолжает писать `lastPlacement` своим правилом и молча пропускает неизвестные templateId — две политики ошибок в одном файле сводятся в едином exit-стадии; lifecycle debug-сессии не менялся: `init_debug` по-прежнему пересоздаёт сессию, поэтому debug-placement живёт только внутри текущей debug-сессии. |
| Stage 7 — единый replay-pipeline | Реализовано: `replay` работает одинаково для campaign и debug. Ветка `if (runtime.sessionSource === 'debug')` в `PhaseManager` удалена вместе с её обоснованием — комментарий «debug battles have no saved placements» устарел ещё на Stage 4/5: debug `start_battle` идёт через тот же `createBattleRuntimeForSession()` и записывает `replaySetup.enemyPlacements`. **Debug replay больше не рероллит врагов** — новая попытка энкаунтера создаётся стартом нового debug-боя, а не replay'ем. `createReplayBattleRuntimeForSession()` живёт рядом с `createBattleRuntimeForSession()` в `battleStart.ts` (тот же pure-core rule, новой записи в `PURE_CORE_FILES` не потребовалось): party status → `projectPlayerBattleSetup(session)` → `buildReplayBattleState()` → `buildInitialBattleParticipants()` → `createBattleRuntimeContext()`. **Фабрика replay принимает `{ session, replaySetup, sessionSource }` и никогда `BattleRuntimeContext`** — только эти три факта переживают границу попытки, поэтому participants/state/mode/turnContext прошлой попытки недоступны по сигнатуре, а не по договорённости. Это чинит реальный баг: `restartBattleRuntime()` пересобирал `state` из свежей проекции, но сохранял `current.participants`; после Stage 6 подтверждённый `lastPlacement` меняет распределение поле/скамейка между попытками, а `wasOnBench` и `isAlive` из устаревшего снимка уходили в `buildPlayerExitInputs()` и `applyVictoryLevelUp()` — тихая неверная персистентность. `buildReplayBattleState()` теперь возвращает `{ state, playerPlacements }`. `restartBattleRuntime()` удалён: после изменения он был буквально `createBattleRuntimeContext()` — разница `resetTurnContextForNewBattle()` vs `createTurnContext()` существует только потому, что эти функции сегодня побайтово идентичны. Сам `resetTurnContextForNewBattle()` сохранён — у него два живых вызова в `PhaseManager` для round-boundary reset, это другая операция. Общий `assertPartyCanStartBattle()` используют обе фабрики, поэтому replay не может построить частичный runtime для невалидной партии. Удалены поля без потребителей: `BattleReplaySetup.enemyGroupId` (единственным читателем была удалённая debug-ветка; ID энкаунтера остаётся на battle-фазе) и `BattleInitResult.race`. `PhaseManager` сведён к трём выражениям без единого условия: `requireBattleRuntime` → `PlayerSessionStore.getSession(runtime.sessionSource)` → одна установка runtime. Контракт закреплён в `tests/core/battleStart.test.ts` (восстановление вражеской формации, проекция игроков из текущей сессии, participants по расстановке текущей попытки, свежий attempt-state, throw на невалидной партии, campaign/debug паритет через явную проекцию, а не сравнение `BattleState`). **Не входило в стадию:** battle-exit персистентность остаётся route-specific до Stage 8; lifecycle debug-сессии не менялся; replay не является детерминированным RNG/combat-снимком (проекция игроков идёт из текущей сессии, а не из снимка прошлой попытки); отдельного debug-reroll action не добавлялось; `resolveTransition()` не менялся — `replay` остаётся in-battle переходом. |
| Stage 8 — единый battle-exit pipeline | Реализовано: результат боя — одна операция над выбранной `PlayerSessionState`. `applyBattleResult({ runtime, session, outcome }, playerBlueprints = PLAYER_UNITS)` в `core/battleExit.ts` (`RosterState` на выходе) композирует три существующих чистых правила в фиксированном порядке: `applyFieldPlacementsToRoster` (правило Stage 6 переиспользовано, второй реализации placement нет) → `applyBattleExitPlayerPersistence` (только HP/life) → `applyVictoryLevelUpPersistence`. **Runtime-параметр — `Pick<BattleRuntimeContext, 'state' \| 'participants'>`**: `sessionSource`, mode, replaySetup, turnContext и pending intentions недоступны по типу, а не по договорённости (тот же приём, что у replay-фабрики Stage 7). Level-up читает **пост-боевой** roster, а не `session.roster` — иначе тихо откатывались бы урон, смерть и revive; оба варианта проходят typecheck одинаково, поэтому инвариант закреплён сценарным тестом. Весь roster вычисляется до записи, запись одна — `PlayerSessionStore.replaceRoster()` в `applyBattleExitPhaseAction({ runtime, outcome })` (`phaseHandlers/battlePhaseHandler.ts`), парном к `applyBattleLifecyclePhaseAction` Stage 6; campaign/debug-условия в нём нет, отсутствие debug-сессии бросает через `PlayerSessionStore`. Прежняя campaign-ветка делала **две** последовательные записи roster (`replaceCampaignRoster` в exit-персистентности и в `applyVictoryLevelUp`) — throw между ними оставлял полупримененный roster. **Изменение поведения debug:** debug теперь персистит HP/life/placement и на победе, и на поражении, а победа повышает уровень **только участникам** (раньше — всем юнитам roster, включая лагерь). Следствие: debug-юниты остаются ранеными и мёртвыми между боями и сессия может остаться без живых — добавлен recovery-маршрут `debug_equip_screen → return_to_debug_level_select → init_debug`; кнопка «Назад» в `UnitSelectionPanel` больше не в `else`-ветке от «Go to Battle» (они не пересекаются: одна по центру снизу, вторая в правом нижнем углу). `wasOnBench` полностью убран из персистентности (остаётся только presentation-метаданными): после Stage 6/7 это снимок начальной попытки, и «missing runtime + wasOnBench» воскрешал юнита. `PlayerExitInput` теперь `{ templateId, runtime }` с **обязательным** runtime-снимком; `computeFieldPlayerPersistence` → `computeBattleExitPlayerPersistence`. Единая политика ошибок: обе оставшиеся функции в `playerUnitPersistence.ts` бросают на отсутствующей roster-записи вместо `continue` — две политики в одном файле, зафиксированные как долг Stage 6, сведены. `buildPlayerExitInputs()` проверяет соответствие участник↔runtime-юнит один-к-одному (дубли с обеих сторон, участник без runtime-юнита, runtime-юнит без участника, участник без deployment) — сегодня инвариант держится структурно: summon'ов в `src/` нет, `autoPlacePlayer()` тотален, мёртвые юниты остаются в `state.units`. **`battle_results` больше не носит динамических боевых данных:** вместо `BattleParticipant[]` фаза несёт `participantSeeds: BattleResultParticipantSeed[]` (`templateId`, `name`, `wasOnBench`, `spriteKey`), а `newLevel`/`isAlive` пересобираются `buildBattleResultsSnapshot(roster, seeds)` в `rebuildSnapshot()` из roster'а сессии `battle_results.sessionSource`. Это убирает две независимые `+1` (в `resolveTransition` по стартовому снимку и в персистентности по roster'у) и исключает протечку стартовых `level`/`isAlive` в экран результатов по типу. `BattleExitOutcome` переехал в `battleRuntimeContext.ts` (к `BattleParticipant`), чтобы `phases.ts` не зависел от логического модуля ради leaf-типа; `BattleResultUnit`/`BattleResultParticipantSeed` **осознанно оставлены** в `phases.ts` — это render-контракты, и `battleResultsSnapshot.ts` импортирует их type-only, как `rosterCampSnapshot.ts`/`upgradeTreeSnapshot.ts`. Отсюда асимметрия boundary-правил: `battleExit.ts` запрещён `core/phases`, `battleResultsSnapshot.ts` — нет. Удалены: `battleExitRouting.ts` + его тест, `GameState.replaceDebugSession()` (последний временный мост Stage 2), `PhaseManager.applyVictoryLevelUp()`, `PhaseManager.buildExitParticipants()`, параметры `derivedExitParticipants`/`exitParticipants` у `resolveTransition()`/`applyActionSideEffects()`. Добавлены guard'ы жизненного цикла: `init_debug` резолвится только из `debug_level_select` (замена debug-сессии при живом battle runtime теперь невозможна), `debug` — только из `main_menu`/`world_map` (**оба** обязательны: экшен диспатчится и из `MainMenu.ts`, и из `WorldMap.ts`; guard только на `main_menu` тихо убил бы вход в debug с карты). В `PURE_CORE_FILES` добавлены `battleExit.ts`, `playerBattleExitProjection.ts`, `battleResultsSnapshot.ts`. Тесты: `tests/core/battleExit.test.ts` (два сценария — победа со смешанным составом и поражение, включая revive), `tests/core/battleExitPhaseAction.test.ts` (table-driven маршрутизация, паритет campaign/debug на структурно равных сессиях, throw при отсутствующем debug-хранилище, ровно одна запись roster). **Не входило в стадию:** полный lifecycle debug-сессии (`reset_debug_session`, уничтожение debug-state, политика очистки при выходе в меню, RNG-lifecycle) — Stage 9; кампанийные world-последствия (`wouldClearMap`/`mapCleared`/`map_victory`) остаются metadata-driven вне roster-правил и не менялись. |
| Stage 9 — debug session lifecycle и save boundary | Реализовано: явный lifecycle debug-сессии — create/reset/dispose — вместо накопления повреждённого состояния в памяти. `src/core/debugLifecycle.ts` — единственный владелец *существования* `DebugBattleState` (`initializeDebugSession`, `resetDebugSession`, `clearDebugSession`); это не `phaseHandlers/*` в стиле camp/progression/inventory, потому что те мутируют содержимое уже существующей сессии через `PlayerSessionStore`, а debug lifecycle создаёт/заменяет/уничтожает сам контейнер сессии и пишет напрямую через `GameState.setDebugState()`/`clearDebugState()` — второго конкурирующего write-пути в `PlayerSessionStore` это не создаёт, потому что `PlayerSessionStore` никогда не владел созданием/уничтожением сессии, только мутацией уже существующей. `createDebugPlayerSession()` зафиксирован как детерминированный контракт (чистая функция от `config`/`playerUnits`/`itemCatalog`, без RNG) — это то, что делает `resetDebugSession()` воспроизводимой операцией; если debug-сборка когда-нибудь потребует случайности, фабрика должна получать явный RNG-параметр, а не читать `PhaseManager`'s gameplay RNG streams. Новый экшен `reset_debug_session` принимается только из `debug_equip_screen` (mutation-only, `resolveTransition` возвращает тот же `GamePhase`) — отклонён из `battle`/`battle_results`, поэтому активная попытка боя не может лишиться своей сессии; `return_to_debug_level_select` остаётся чисто навигационным, как и раньше. `PhaseManager` получил приватный `resetGameplayRngStreams()` — единая точка сброса RNG streams, вызываемая из `init_debug`, `reset_debug_session`, `exit_to_menu`, `new_game`; раньше `exit_to_menu` вообще не имел side-effect ветки и не чистил ни debug state (несмотря на существующий, но никогда не вызываемый `GameState.clearDebugState()`), ни RNG. Теперь `exit_to_menu` и `new_game` явно вызывают `clearDebugSession()` и defensively чистят battle runtime независимо от фазы, из которой они диспатчатся — старая generic очистка runtime при выходе из `battle`-фазы (`PhaseManager.transition()`) остаётся как idempotent инвариант, но не единственный механизм очистки. В `UnitSelectionPanel` добавлена кнопка «Reset Session» (`onResetDebugSession`), видимая только для `debug_equip_screen` и рендерящаяся даже когда живых debug-юнитов не осталось — это прямой recovery-путь, не требующий выхода на `debug_level_select`. **Save boundary как контракт, не как реализация:** `src/save/saveTypes.ts` — `SaveRepository { load(saveId): CampaignState; save(saveId, state): void }`, ничего кроме `CampaignState` через границу не проходит; ни сериализации, ни storage, ни UI, ни save-экшенов в этой стадии нет. `scripts/check-boundaries.mjs` получил closed allowlist-правило для `save/**` (`save`, `campaign`, `shared`; никакого `phaser`) по образцу `world/**`, и `'save'` добавлен в blocklist каждого существующего layer, кроме `core` (будущий вызывающий `SaveRepository`) — это закрывает задокументированный в разделе "Boundary enforcement" gap заранее, пока у `save/` нет ни одного реального потребителя. |
| Stage 10 — Phaser isolation boundary (core/**) | Реализовано: `core/**` больше не зависит от Phaser ни в каком виде — `PhaseManager.ts` (был `import Phaser from 'phaser'`, `private game!: Phaser.Game`, приватный `syncPhaserScenes()`/`GAME_SCENES`) делегирует запуск/остановку сцен новому интерфейсу `PhaseSceneSynchronizer` (`core/phaseSceneSynchronizer.ts`: `sync(phase: GamePhase): void`, без Phaser, без scene keys). Единственная реализация — `PhaserSceneSynchronizer` (`scenes/phaserSceneSynchronizer.ts`), которая переносит прежний маппинг `GamePhase.type → scene key` в **compile-time-exhaustive** `Record<GamePhase['type'], GameplaySceneKey>` — добавление нового варианта `GamePhase` без записи в этом `Record` теперь ошибка сборки, а не тихий no-op (прежний `switch` с `default: return` такой защиты не давал). Импорт `Phaser` в адаптере — **type-only** (`import type Phaser from 'phaser'`), поэтому unit-тесты адаптера не грузят настоящий Phaser в Node. `PhaseManager.init(sceneSynchronizer)` заменил `init(game)`; `Boot.ts` теперь вызывает `PhaseManager.init(new PhaserSceneSynchronizer(this.game))`. **Синхронизатор — precondition навигации**, проверяемый приватным `requireSceneSynchronizer()` **до** `applyActionSideEffects()` для любого навигационного перехода (`next !== this.phase`), а не только в финальном вызове `sync()` — отсутствие `init()` поэтому прерывает переход с нулевой мутацией состояния, а не частично мутирует `GameState`; сброс `this.lastBattleTransition = null` тоже перенесён за preflight-проверку, потому что это тоже наблюдаемое состояние `PhaseManager` (`getLastBattleTransition()`). Rejected и mutation-only переходы синхронизатора не требуют. `PhaseManagerClass` теперь экспортируется наравне с синглтоном `PhaseManager`, что делает orchestration изолированно тестируемым через fake `PhaseSceneSynchronizer` (`tests/core/phaseManagerOrchestration.test.ts`). `core/EventBus.ts` — раньше `new Phaser.Events.EventEmitter()`, теперь небольшой самописный Phaser-независимый emitter (`on`/`off`/`emit`, identity по `(event, handler, context)`); `Events.STATE_CHANGED` не изменился. `core/sceneEvents.ts` переехал в `scenes/sceneEvents.ts` без изменений логики (нулевые вызывающие на момент переноса) — Phaser scene-lifecycle биндинг не относится к `core`. `scripts/check-boundaries.mjs`: `core/**`-правило получило глобальный запрет `'phaser'` в общем blocklist (ловит bare/type-only/dynamic import); `PURE_CORE_FILES` **не тронут** — его отдельные `'phaser'`-записи для 7 файлов оставлены намеренно как defense in depth поверх общего правила, а не задедублены. **Не входило в стадию:** `resolveTransition()`, side effects, `rebuildSnapshot()`, форма `GamePhase`/`PhaseAction`, singleton API для сцен — не менялись; file-level import allowlist для `PhaseManager.ts` (упомянутый как уже реализованный в старой версии `src/core/CLAUDE.md` — на деле никогда не существовал в `check-boundaries.mjs`) не добавлен и явно отложен до стадии, декомпозирующей side effects/snapshot building `PhaseManager` — до этого его широкий набор domain/runtime импортов легитимен, а узкий allowlist сейчас либо ничего не защитил бы, либо сломал бы текущую реализацию. |
