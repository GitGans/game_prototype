| Решение                              | Реализация                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Роль `PhaseManager`                  | Согласовано: `PhaseManager` остается единственным lifecycle owner. Он принимает `transition(action)`, вызывает pure `resolveTransition`, делегирует side effects и snapshot rebuild тонким phase handlers / pure modules, синхронизирует Phaser scenes и эмитит notification-only event. Он не содержит тяжелую business logic.                                                                                                                 |
| Декомпозиция phase logic             | Согласовано: использовать `core/phaseHandlers/` по доменам фаз: `battlePhaseHandler`, `worldPhaseHandler`, `campPhaseHandler`, `shopPhaseHandler`, `narrativePhaseHandler`, `dayPhaseHandler`, `debugPhaseHandler`. Handler — тонкий adapter: resolve/apply/rebuild для своего домена, но тяжелая логика уходит в pure modules.                                                                                                                 |
| Временный split по функциям          | Согласовано: не делать целевой промежуточный split `phaseTransitions.ts / phaseSideEffects.ts / phaseSnapshotBuilders.ts`. Сразу идти в domain phase handlers, чтобы не создавать временный техдолг.                                                                                                                                                                                                                                            |
| Структура доменов                    | Согласовано: выделить top-level домены: `campaign/`, `inventory/`, `progression/`, `dialogue/`, `debug/`, `save/`. `core/` остается orchestration layer, `battle/` сохраняет runtime battle/skill logic.                                                                                                                                                                                                                                        |
| `CampaignState`                      | Реализовано (Stage 1): `CampaignState { roster, inventory, world, money }` — реальный nested-объект в `src/campaign/campaignState.ts`, JSON-compatible, единственный будущий save source. `roster: RosterState` и `inventory: InventoryState` — общие типы с debug-сессией (`src/progression`, `src/inventory`), но campaign и debug никогда не делят runtime-инстансы. `world: WorldState` содержит `currentMapId`, `partyPos`, `subMapStates` — текущая карта и позиция партии являются persistent campaign-данными, а не rendering state (иначе save не мог бы восстановить, где стоит партия). `shops` и `narrative` будут добавлены только когда появятся соответствующие runtime-домены — до тех пор они не резервируются как пустые заглушки.                                                                                                                                                                                                                                                                             |
| Где хранить runtime state            | Согласовано: типы и pure mutations живут в доменных модулях; runtime container текущего состояния остается в `core/GameState.ts` или `core/AppState.ts`. Он хранит текущий `CampaignState`, `BattleState`, debug runtime refs. PhaseManager обращается к текущему state через core container.                                                                                                                                                   |
| `battleSetup`                        | Согласовано: `battleSetup` не является campaign-domain модулем. Это cross-domain projection layer в `core/battleSetupProjection.ts` или `core/battleSetup.ts`, потому что он связывает campaign, inventory, progression, debug, data и battle runtime contracts.                                                                                                                                                                                |
| Debug battle setup                   | Согласовано: отдельные builders с единым output contract: `buildCampaignBattleSetup(campaignState, encounter) → BattleSetupContext` и `buildDebugBattleSetup(debugState) → BattleSetupContext`. Не использовать `isDebug?` внутри одного общего campaign builder.                                                                                                                                                                               |
| Day system                           | Согласовано: return-event model через ordered pure steps. Каждый step получает state и возвращает `{ nextState, events }`. Порядок явный: например camp healing → shop refresh → map events → narrative triggers. `DayEvent[]` идет в `day_end` phase snapshot.                                                                                                                                                                                 |
| Save system                          | Согласовано: отдельный `save/` домен: `SaveSystem.ts`, `saveTypes.ts`, `saveSerializer.ts`, `saveMigrations.ts`. Убрать обязательный autosave: по gameplay plan сохранение ручное.                                                                                                                                                                                                                                                              |
| Save source                          | Согласовано: save source только campaign-level state. `GamePhase`, `BattleState`, Phaser scene state и UI state не сериализуются. Campaign state должен быть plain JSON-compatible.                                                                                                                                                                                                                                                             |
| `currentHp: number \| null`          | Согласовано: допустимый invariant для sparse state. `null` означает “полное HP относительно текущего resolved max HP”. Это должно быть явно задокументировано в типе и учитываться при изменении max HP через progression/equipment/class changes.                                                                                                                                                                                              |
| EventBus                             | Согласовано: EventBus остается только notification channel. Он может эмитить `STATE_CHANGED`, но не переносит domain payload. Единственный render data source для scenes — `PhaseManager.getPhase()`.                                                                                                                                                                                                                                           |
| Battle/skill safety                  | Согласовано: явно зафиксировать safety invariants: 2×3 field per side, shapes, targeting rules, damage/effect/instant matrices, damage modifiers, post-damage vampirism, active effect limit/ticking/expiration, bench preview, replay, debug battle. Skill system расширяется cooldowns/charges, но не заменяется.                                                                                                                             |
| `GamePhase`                          | Согласовано: `GamePhase` — render/read model, не save source. Каждая scene читает все render data из phase snapshot и route input через `PhaseManager.transition()`.                                                                                                                                                                                                                                                                            |
| New `GamePhase` types                | Согласовано: добавить фазы `shop`, `dialogue`, `cutscene`, `day_end`. `map_transition` добавлять только если будет отдельный экран перехода; для мгновенного перехода достаточно `world_map` с новым `mapId/partyPos`.                                                                                                                                                                                                                          |
| Inventory/shops                      | Согласовано: inventory/shop state агрегируется внутри `CampaignState`, а правила inventory/equipment/shop stock живут в pure modules в `inventory/`. Shops получают persistent must-have stock и daily generated assortment.                                                                                                                                                                                                                    |
| Progression                          | Согласовано: `progression/` — отдельный домен. Он отвечает за upgrades, class/evolution, stat/skill/sprite resolving, movement speed, equipment restrictions. Battle получает только resolved runtime input.                                                                                                                                                                                                                                    |
| Dialogue/cutscenes                   | Согласовано: save flags живут в `CampaignState.narrative`, а условия, последовательности и read-model logic живут в pure modules `dialogue/`. Dialogue/cutscene scenes получают data через `GamePhase`.                                                                                                                                                                                                                                         |
| Dependency map                       | Согласовано: strict dependency map. `campaign/` не зависит от `battle/`; связь campaign/debug/inventory/progression с battle идет только через `core/battleSetupProjection`. `battle/` не зависит от campaign/core.                                                                                                                                                                                                                             |
| Boundary enforcement                 | Согласовано: добавить явные layer rules в docs и `scripts/check-boundaries.mjs`. Проверять imports, `import type`, `export from`, dynamic import. Enforcement включить в `npm run build` после завершения temporary bridges.                                                                                                                                                                                                                    |
| Migration strategy                   | Согласовано: temporary bridge exports допустимы только как миграционный инструмент. Они должны быть явно помечены, иметь короткий срок жизни и удаляться до финального boundary enforcement.                                                                                                                                                                                                                                                    |
| Tests для pure functions             | Согласовано: добавить unit tests для pure modules: battle placement helpers, battle setup projection, day steps, inventory/shop rules, progression resolving, save serializer/migrations.                                                                                                                                                                                                                                                       |
| Итоговая структура                   | Согласовано: гибридный подход: second plan domain phase handlers + expanded top-level domains из моего плана. `core/` тонкий, domains чистые, `battle/` сохраняет текущую боевую логику.                                                                                                                                                                                                                                                        |
| Явная dependency layering            | Согласовано добавить. Правила: `shared/`, `data/` не зависят от game modules; `battle/` только `shared/`, `data/`; `campaign/`, `inventory/`, `progression/`, `dialogue/`, `world/` только `shared/`, `data/`, допустимые sibling-domain contracts без циклов; `core/` может зависеть от domain modules; `scenes/` только `core/`, `objects/`, `ui/`; `objects/` только `ui/`, `shared/`, `data/` и render contracts; `ui/` без game knowledge. |
| CampaignState initialization         | Согласовано добавить. Начальная кампания создается явной pure function: `initCampaignState(defs): CampaignState`. Не в `PhaseManager`, не в constructor `GameState`. PhaseManager только вызывает factory при `new_game`.                                                                                                                                                                                                                       |
| Расширение `data/`                   | Согласовано добавить. Для новых систем сразу заводятся content definition files: `shopDefinitions.ts`, `dialogueDefinitions.ts`, `cutsceneDefinitions.ts`, при необходимости `dayEventDefinitions.ts`/`mapEventDefinitions.ts`. `data/` содержит definitions only, без runtime state.                                                                                                                                                           |
| Guardrail для `objects/`             | Согласовано добавить. `objects/` может импортировать snapshot/render contracts из `shared/` и при необходимости типы phase snapshots, но не должен читать live `GameState`, мутировать state или вызывать `PhaseManager`. Game-specific components получают данные и callbacks снаружи.                                                                                                                                                         |
| Guardrail для sibling-domain imports | Согласовано добавить. Импорты между `campaign/`, `inventory/`, `progression/`, `dialogue/`, `world/` держать минимальными. Если одному домену нужны данные другого, предпочтительно передавать их параметрами из `core/` или выносить общий contract в `shared/`, чтобы не получить скрытый новый монолит.                                                                                                                                      |
| Stage 2 — session routing и equipment flow | Реализовано: `PlayerSessionSource = 'campaign' \| 'debug'` — core-only routing key на `equip_screen`/`debug_equip_screen` (`src/core/playerSessionState.ts`, `phases.ts`), считывается один раз из текущей фазы, никогда не выводится из `phase.type`/`returnPhase`/backpack ID. `PlayerSessionStore` (`src/core/playerSessionStore.ts`) — единственный storage-only seam между `sessionSource` и `GameState`; не содержит domain-правил. `equipItem`/`unequipItem`/`buildBackpackSnapshot`/`buildEquipmentSnapshot` переведены на `InventoryState`; shared backpack резолвится структурно через `requireSharedBackpack` — ни одно правило больше не сравнивает `backpack_shared`/`backpack_debug`. `inventoryPhaseHandler.ts` (`core/phaseHandlers/`) — единственная точка мутации equip/unequip; не знает про Phaser, `GameState`, campaign/debug. `equipmentScreenSnapshot.ts` — один shared projection builder для обоих equip-экранов; `PhaseManager.buildUnitTabSnapshots()` удалён. `GameState.replaceDebugSession()` остаётся как temporary migration bridge — помечен `@deprecated`, equipment-код через него больше не идёт; удаление запланировано на Stage 8 после того как Stage 3 (camp/upgrade) и Stage 7 (battle exit) уберут свои call sites. |
